Serving a branching LLM-agent simulation: 251 counterfactual branches on 4 × A100

Three parts: serving results, scheduling the branches together (simulated, calibrated on this run) and what the simulation found (which core user spread the rumour fastest).

Baseline run for a systems study of intervention-aware LLM serving. Branches run one at a time per GPU, with the prefix cache flushed before each. Run of 2026-11-25 (Slurm job 63508559).

Setup

  • Workload. An OASIS social-media simulation with 250 LLM agents (36 well-connected "core" users). After a warm-up, the world is forked at step 6: a control branch, plus one branch per agent in which that agent posts the same rumour. Each branch then runs steps 7–16. Agents are activated by a seeded draw, so the same agents act at the same step in every branch. Only the content they see differs.
  • Model and server. Qwen3-4B-Instruct-2507 on SGLang 0.5.10.post1 with deterministic inference (Triton attention), the lpm schedule, chunked prefill of 4,096 tokens, and HiCache (host KV tier at 1.5× the GPU pool, write-through, LRU). The GPU KV pool holds 431k tokens. Every call returns top-5 logprobs.
  • Hardware. One whole node, held exclusively: 4 × A100-SXM4-80GB (NVLink), 2 × 32-core Ice Lake, 1 TB RAM. One server per GPU. Each server runs about 63 branches in sequence, with its client's cores and memory bound to that GPU's NUMA node. All 36 nodes of the partition are this type.
  • Comparison run. The MIG comparison (figure 3) uses an earlier test on one MIG 3g.20gb slice of an A100, with the same server settings and the same four branches.

Scheduling the branches together (simulated)

The run above wastes most of its reuse: 68% of prompt tokens had already been computed by another branch, but only 30% came from cache. How should one server order 63 branches' calls to recover that? Every branch's prompts are the same under any schedule (deterministic inference), so the recorded token stream of this run can be replayed through a cache simulator for any schedule. The simulator and a step-time model are calibrated on this run (S1, S2), then used to compare schedules (S3–S5). These are predictions; a GPU validation run comes next.

  • Run every branch together and order requests by agent. All 63 branches per GPU together, with the proxy releasing each step's calls agent by agent, are predicted at 4.38 h per GPU against 5.45 h for the schedule as run (20% less), computing about half as many prompt tokens.
  • Negative result: shrinking groups as the cache fills. The scheduler first proposed splitting groups when their predicted working set outgrows the cache (63 branches early, down to 1 by the last step). It is slower than fixed groups of 16 (4.75 h). The working-set model was too pessimistic: calls for the same agent run back to back, so its shared prefix is reused while still resident, and splitting only gives up reuse at the late steps, where prompts are longest.
  • Order is what protects a small cache. If each branch sends its calls as one burst, large groups thrash in a small cache (at 63k tokens, all 63 together become slower than one at a time). Ordering by agent keeps them near 4.4 h at every cache size tested.

What the run found: which core user spread the rumour fastest

Each seeded branch starts from the same world at step 6. One agent posts the same water-contamination rumour; the branches then run steps 7–16. Exposure counts agents whose feed showed the seed post or a repost or quote of it. Engagement counts agents who liked, commented on, reposted or quoted it, or followed the poster.

What is compared. The 36 core users as seeders, against one regular user as a control: agent 36, the lowest-id regular user, chosen by rule before looking at outcomes. Regular users are not compared with each other. In this follow graph they have no followers, and their reach turned out to hinge on one sampled decision by another agent (see below).

  • Fastest: agent 18 (36 followers). Its rumour reached 74 of 250 agents (29.6%), with 37 engaging and 9 reposts or quotes; 10% by step 10, 25% by step 15. Next: agent 23 (70) and agent 34 (62). Slowest: agent 11 (27).
  • Every core seeder beat the control. Median core reach was 20.2% (range 10.8–29.6%), against 5.2% (13 agents) for the control: 3.9× at the median. Engagement: 8.0% vs 1.6%. All 36 core seeders passed 10% by step 16; only 2 passed 25%.
  • Spread is slow and mostly linear. Reposts are few (median 2 per branch), so the seed post's own audience carries most of the reach. Engagement is mostly comments: 616 commenting agents vs 109 liking and 106 reposting, summed over core branches.
  • Follower count explains only part of it. Spearman 0.45 with reach and 0.27 with engagement across the 36 core seeders (19–43 followers). Agent 23 is second with only 25 followers; agent 30 has the most (43) and is fourth.
  • One early repost matters here too. Core user 22 reposted the rumour at step 7 in 28 of the 35 other core branches; those reached a median 21.6% against 15.6% for the 7 where it didn't. In the regular branches this decision was shown to flip on nothing but the author's id number, so part of the gaps between core seeders is likely sampling luck rather than the seeder.

Limits. The follow graph copies the OASIS paper's misinformation setup (App. E.2): regular users follow the core users who share an interest topic, and the paper describes no other follows. We read that as none, so regular users have no followers. There is one run per seeder: sampling uses temperature 0.7 with seeds fixed per call, and agents are activated by a seeded draw that is the same in every branch, so differences of a few agents between core seeders may not hold up across repeats. The model is Qwen3-4B, not the paper's Llama-3-8B, in a 250-agent scaled-down world.

Caveats (serving results)

  • Extra GPU and node telemetry (DCGM counters, 1-s PCIe, per-core CPU) was attached 2.1 h into the 5.7 h job, so figures 6 and 7 cover only the last 3.6 h. That monitor ran as one extra process on core 0. Branches took 327.7 s on average before it attached (93 branches) and 325.5 s after (155 branches).
  • The MIG and A100 runs are separate jobs on different nodes, though they use the same code, server flags and branches.
  • Cross-branch reuse is measured offline, as the longest common token prefix with other branches' prompts for the same agent and step. It is an upper bound on what running branches together could reuse, not a measured speed-up.
  • 286 of 82,827 requests (0.35%) ended in an abort. 248 of these are one call, agent 147 at step 7, which aborted in 248 of the 251 branches. So the aborts are a property of that prompt, not of load.
  • The concurrent counterpart of this run, which would test cross-branch reuse directly, has not been run yet. The scheduling section's numbers are predictions from a simulator calibrated on this run.
